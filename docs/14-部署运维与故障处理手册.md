# 锦程 ERP Web 部署运维与故障处理手册

## 1. 环境基线

| 环境        | 用途                      | 数据要求                     |
| ----------- | ------------------------- | ---------------------------- |
| development | 开发者本机                | 生成或脱敏测试数据           |
| staging     | UAT、迁移、性能和恢复演练 | 脱敏后接近生产规模           |
| production  | 正式业务                  | 独立密钥、账号、数据库和存储 |

本地基线：Node.js 24、pnpm 11、Docker、Git；具体版本以根目录 `package.json` 和 `pnpm-lock.yaml` 为准。

## 2. 本地启动

```powershell
Copy-Item .env.example .env
pnpm install
docker compose -f infra/docker-compose.yml up -d
pnpm db:validate
pnpm db:generate
pnpm dev
```

默认 Web 为 `http://localhost:3000`，API 文档为 `http://localhost:3100/docs`。示例密码只用于本机，首次启动前必须替换。

## 3. 生产拓扑

- HTTPS 反向代理 → Web 容器和 API 容器。
- Worker 独立运行，处理导入、同步、通知、报表和重试。
- PostgreSQL 使用独立实例；Redis 只保存可重建队列/缓存；附件进入对象存储。
- 生产 `.env` 和密钥由服务器密钥管理或受控配置提供，不进入 GitHub。
- 试点使用 Docker Compose；达到明确规模和运维需求后再评估编排平台。

当前试点服务器已确定使用宝塔面板，并复用现有项目的 GitHub Actions + SSH + PM2 + Nginx 发布方式，以宝塔方式为准（上一条的「试点 Docker Compose」仅保留为后续独立化方案，不适用于当前宝塔服务器）。锦程 ERP 的具体目录、端口、数据库备份和自动部署流程见 `19-宝塔GitHub自动部署.md`；仓库尚未配置 SSH Secrets 时的首次部署走该文档「路径 B」的 `scripts/baota-first-deploy.sh`。

## 4. 发布检查

1. 变更单包含版本、需求、迁移、风险、回滚和负责人。
2. CI 完成构建、lint、类型检查、测试、依赖和密钥扫描。
3. 数据库迁移先在 staging 用生产规模副本演练。
4. 部署 API/Worker/Web，依次检查健康接口、数据库、队列和关键页面。
5. 用真实角色执行登录、查货和一条只读业务验证；写入验证使用专用测试单据。
6. 观察错误率、延迟、队列和数据库至少 30 分钟后关闭发布窗口。

## 5. 备份与恢复

- 目标：RPO ≤ 15 分钟，RTO ≤ 2 小时。
- PostgreSQL 每日全量备份，WAL/增量至少每 15 分钟可恢复；备份异地、加密并设置保留期。
- 对象存储启用版本和生命周期；配置、密钥和迁移脚本单独备份。
- 每季度至少一次从空环境恢复，并抽查库存、资金、单据、权限和审计。
- 未完成恢复演练的备份不能视为可用备份。

## 6. 监控与告警

- Web/API：可用性、P95 延迟、4xx/5xx、登录失败和限流。
- 数据库：连接数、慢查询、锁等待、复制/WAL、磁盘和备份。
- Worker/Redis：队列堆积、重试、死信、任务耗时。
- 业务：重复 IMEI、库存对账差异、在途超时、付款到货差异、同步失败。
- 每条关键告警配置负责人、通知渠道、响应时限和升级人。

## 7. 故障分级

| 级别 | 示例                                          | 初始响应 | 处理原则                                 |
| ---- | --------------------------------------------- | -------: | ---------------------------------------- |
| P0   | 库存/资金错账、全站不可用、越权泄露、无法恢复 |  10 分钟 | 停止相关写入，保全证据，启动负责人和回退 |
| P1   | 单门店主链路不可用、队列持续堆积              |  30 分钟 | 降级或隔离，明确修复时限                 |
| P2   | 非关键报表、个别集成延迟                      |   4 小时 | 进入缺陷和计划修复                       |

## 8. P0 处置步骤

1. 确认影响范围和开始时间，暂停受影响写操作而不是盲目重启。
2. 保存 request_id、应用日志、数据库状态、队列和当前版本。
3. 判断应用回滚、前向修复或数据重放；禁止直接手改生产余额。
4. 恢复后执行库存/资金对账和权限验证。
5. 形成事故复盘：时间线、根因、影响、修复、预防措施和负责人。

## 9. 换机与灾备注意

- 仓库可重新克隆；`node_modules`、`.next`、`dist` 和 Prisma 生成代码不作为备份。
- `.env`、生产密钥和真实数据通过独立安全渠道迁移。
- 新电脑运行完整质量门禁后再开始改动，避免环境差异造成错误结论。
