# 锦程 ERP Web 总体架构

## 1. 架构结论

首期采用“Next.js 响应式 Web + NestJS 模块化单体 API + 独立后台 Worker + PostgreSQL + Redis + 对象存储”。这能在保持交易一致性和清晰边界的同时，以最小部署复杂度尽快上线。未来 PC、APP、小程序通过版本化 REST API 和统一身份体系接入。

## 2. 逻辑分层

```text
员工/店长/库管/财务/运营/老板
                │
        响应式 Web / PWA
                │ HTTPS
      反向代理 / API 边界 / 限流
                │
    NestJS 模块化单体 API（/api/v1）
  ┌─────────────┼────────────────┐
  │             │                │
业务模块      权限与审计       Integration Center
  │             │                │
  └────────── PostgreSQL ─────────┘
                │ 事务发件箱
             Worker / Redis 队列
                │
     企微、短视频、小程序、通知、报表
```

## 3. 系统组件

### 3.1 Web 端

- 角色化首页：销售、店长、库管、财务、人事、运营、老板看到不同工作台。
- 全局查货：支持型号、品牌、颜色、容量、SKU、商品编码、条码、IMEI、SN。
- 响应式：复杂管理页面优先桌面；扫码确认、个人库存、待办、回访优先手机。
- PWA：首期支持添加到桌面、基础缓存和快速启动；业务写入不依赖离线缓存。
- 可访问性：键盘操作、清晰焦点、表单错误提示、可读对比度。

### 3.2 API 端模块边界

| 模块 | 职责 | 关键输出 |
|---|---|---|
| Identity & Access | 登录、会话、账号冻结、角色、范围、字段和审批权限 | 权限判定、脱敏策略、审计上下文 |
| Organization | 公司、区域、门店、部门、岗位、员工、离职交接 | 统一 employee_id/store_id |
| Catalog | 品牌、品类、商品、SKU、条码、序列号规则、价格参考 | product_id/sku_id |
| Inventory | 仓库、个人库、序列号、数量余额、库存流水、库龄、盘点、异常 | 可售库存、责任库存、资金占用 |
| Transfer | 调拨申请、锁定、出库、在途、收货、拒收和差异 | 握手状态机、待办 |
| Procurement | 供应商、采购单、审批、付款、到货、收货差异 | 已付未到、应付、采购成本 |
| Sales | 销售单、收款、扣库存、退换货、优惠、多人业绩 | 销售额、毛利、客户归因 |
| CRM | 统一客户、企微/会员映射、回访、意向、跟进、漏斗 | customer_id、下次跟进 |
| People Operations | 考勤、目标、视频、直播、员工 360 和绩效 | 动作/结果指标 |
| Finance | 业务收支、退款、应收应付、库存资金、毛利口径 | 业务财务视图 |
| Task & Event | 待办、审批、提醒、异常、业务事件 | 可操作工作队列 |
| Integration Center | 外部身份映射、同步任务、原始载荷、重试、对账 | 幂等同步、错误隔离 |
| Reporting | 日周月报、老板驾驶舱、导出 | 经营快照与趋势 |
| Audit | 操作人、来源、前后值、时间、请求链路 | 不可抵赖的审计记录 |

### 3.3 后台 Worker

Worker 处理外部平台同步、批量导入、报表生成、消息通知、重试和数据对账。主 API 只提交任务和返回任务编号，不在用户请求中等待长任务完成。

## 4. 数据架构

### 4.1 主数据

- organization、store、department、employee、user_account。
- role、permission、data_scope、field_policy、approval_policy。
- product、sku、barcode、supplier、customer、warehouse。
- external_identity：内部 ID 与企微、短视频、小程序、直播平台 ID 的映射。

### 4.2 业务单据

- purchase_order、purchase_payment、purchase_receipt、purchase_difference。
- transfer_order、transfer_shipment、transfer_receipt、transfer_exception。
- sales_order、sales_payment、sales_return、sales_performance_allocation。
- stocktake_order、damage_order、borrow_order、after_sales_order。
- followup_record、content_task、live_session、attendance_record。

### 4.3 库存账设计

- 序列号商品：每台设备有唯一 serial_id 和 IMEI/SN；当前状态用于查询，完整变化保存在不可变库存流水中。
- 数量商品：以 SKU × 仓库保存查询余额；余额只能由库存流水汇总或事务内同步更新。
- 任何库存变动必须关联 document_id、movement_type、来源库、目标库、操作人和发生时间。
- 接收方确认前，调拨货物处于 IN_TRANSIT/PENDING_CONFIRM，不能计入目标门店正常可售库存。
- 采用数据库事务和行级锁/乐观版本控制，防止同一台设备重复销售或重复调拨。

### 4.4 资金与成本

- 序列号商品使用单机实际成本。
- 数量商品建议首期使用移动加权平均成本；最终以财务确认口径为准。
- 付款、收款、退款、费用和应收应付使用业务资金流水，不直接冒充会计总账。
- 审批后金额修改必须走变更或冲销单，不覆盖历史。

### 4.5 可靠事件

业务写入、审计日志和 outbox_event 在同一数据库事务内提交。Worker 发布成功后标记 published_at，失败可重试，避免“单据成功但通知/报表/同步丢失”。

## 5. API 规范

- 路径版本：`/api/v1`；资源名使用复数名词。
- 契约：OpenAPI 自动生成，并作为 Web、未来 APP/PC/小程序的接口依据。
- 写操作支持 `Idempotency-Key`，防止扫码、网络重试和 webhook 重复入账。
- 列表统一分页、筛选、排序和字段选择；导出走异步任务。
- 错误返回统一业务码、用户提示、request_id 和可定位日志信息。
- Webhook 验签、重放防护、原始载荷留存和死信重试。
- 内部管理 API 与小程序公网 API 分开授权、限流和数据范围。

## 6. 权限模型

最终权限 = Role × DataScope × Action × Field × Approval。

- Role：人事、财务、库管、店长、销售、运营、管理员、老板等，可一人多角色。
- DataScope：本人、本门店、指定门店、指定区域、全公司。
- Action：查看、创建、编辑、提交、确认、审批、作废、导出等。
- Field：成本、毛利、账户、手机号等字段按策略隐藏、脱敏或只读。
- Approval：采购、付款、折扣、库存调整按金额或数量额度控制。
- 所有接口在服务端检查权限，前端隐藏菜单不是安全控制。

## 7. 搜索策略

- IMEI、SN、条码、商品编码使用唯一/普通 B-tree 索引，精确搜索优先。
- 型号、品牌、颜色、容量使用规范化字段、组合索引和 PostgreSQL 文本/模糊搜索。
- 首期不引入 Elasticsearch；只有 PostgreSQL 在真实数据量下无法达到验收指标时再增加专用搜索服务。
- 搜索结果在数据库查询层应用门店范围和字段脱敏，禁止先查全量再在前端过滤。

## 8. 部署与环境

### 8.1 环境

- development：开发者本机，使用独立测试数据。
- staging：与生产拓扑一致，用于迁移、性能、UAT 和恢复演练。
- production：独立账号、数据库、密钥、对象存储和监控。

### 8.2 试点生产拓扑

- Linux 主机或合规云主机。
- 反向代理提供 HTTPS、请求大小限制、限流和基础防护。
- Web、API、Worker 使用独立容器；PostgreSQL 优先使用托管实例或独立主机。
- Redis 仅保存可重建队列/缓存数据；对象存储保存附件和导入文件。
- 每日全量备份 + 持续/高频增量备份；备份必须异地保存并加密。
- 试点期使用 Docker Compose；不为“看起来先进”引入 Kubernetes。

## 9. 可观测性与运维

- 每个请求携带 request_id，日志使用结构化 JSON。
- 监控接口延迟、错误率、数据库连接、慢查询、队列堆积、同步失败、磁盘和备份状态。
- 对采购、调拨、销售、库存调整等关键状态转换记录业务指标和审计事件。
- 发布使用数据库迁移检查、健康检查、自动回滚或前向修复方案。

## 10. 未来多端演进

- PC：优先 Tauri/桌面壳复用 Web；只有打印、串口、离线等能力需要时开发本地插件。
- APP：复用 REST API 和契约；移动端只实现高频任务，不复制整套后台菜单。
- 小程序：通过专用公网 BFF 暴露会员、订单、积分、查询等最小能力。
- 若出现明确的独立伸缩、独立发布或团队边界，再从模块化单体拆出 Integration、Reporting 等服务。
